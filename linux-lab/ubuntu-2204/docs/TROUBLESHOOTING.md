# Ubuntu 22.04.2 Packer build — investigation and learning notes

## 1. Working environment and ISO switch

The lab used Kali Linux + VMware Workstation 17.6.3 + Packer 1.16.1 with VMware plugin 2.1.6. Packer initially installed as an older version (1.6.6) and was upgraded. Originally planning Ubuntu 24.04, we switched to an already-downloaded `ubuntu-22.04.2-live-server-amd64.iso` to avoid another download. The **local** folder was still called `ubuntu2404`, while the VM name/output changed to **Ubuntu 22.04**. A local ISO must be accompanied by a correct SHA-256 checksum.

## 2. NoCloud autoinstall and password problems

Packer hosted the `http/user-data` and `http/meta-data` files using `http_directory` and passed a NoCloud HTTP seed URL to the Ubuntu installer via GRUB. The installed account was `packer` with SSH enabled. An early installer screen displayed `password: '<NULL>'`, and subsequent authentication failed. The correction was to generate a **SHA-512 crypt password hash** with `openssl passwd -6` and place the hash in the autoinstall `identity.password` field, while also passing the corresponding **plaintext** password to Packer's `ssh_password` at runtime. A SHA-512 hash cannot be used directly as the SSH login password.

For this repository the password hash is generated dynamically and kept in ignored `http/user-data`, never checked into Git.

## 3. Installer updates failure

The installer reported an exception in `unattended-upgrades -v` with a non-zero exit status of 1. Installation had already progressed through Ubuntu/GRUB installation, but post-install updates failed and Packer remained waiting for SSH. We investigated rebooting and avoiding unnecessary updates. This error is not proof of incorrect Packer connectivity; it can happen before SSH becomes available.

**Important distinction:** `refresh-installer.update: false` disables updating the Subiquity installer; it does not disable target system package upgrades. Canonical's documented autoinstall `updates` choices are `security` and `all`, with `security` the default. Do **not** assume `updates: none` is valid. To reproduce the exact final workaround that succeeded locally, compare with the original successful `http/user-data` on your Kali host; that exact version was not recoverable from the conversation.

Useful commands on the **installer console** while the VM is running:

```bash
sudo tail -n 100 /var/log/installer/subiquity-server-debug.log
sudo grep -R -n 'unattended-upgrades\|failed\|error' /var/log/installer/ 2>/dev/null | tail -n 80
sudo journalctl -b --no-pager | tail -n 120
```

APT mirrors/reachability and the installer's captured logs should be checked before modifying autoinstall YAML.

## 4. GRUB/autoinstall boot issues

GRUB command mode (`c`) was used to run `/casper/vmlinuz` with `autoinstall` and `ds=nocloud-net` pointing to the HTTP seed generated by Packer, load `/casper/initrd`, and boot. A restart or boot attempt can re-enter the installation ISO, so ensure the VM proceeds to its installed virtual disk after the OS has been copied. The exact successful local `boot_wait` timing was not preserved; the checked-in settings are therefore a **candidate**.

## 5. Completed result

The build was completed and Ubuntu could be seen by VMware's REST API at an output VMX path equivalent to:

```text
~/Projects/mt-packer26/ubuntu2404/output/ubuntu-2204/ubuntu-2204-packer.vmx
```

The subsequent VMware REST API listed this machine with **2 vCPU and 4096 MB RAM**. These values are observed from the later integration conversation. No specific Ubuntu patch set, VMware Tools version, final SSH username status, or exact original final HCL content was supplied for independent validation.

## 6. Later Terraform attempt (not yet verified as working)

The later conversation explored Terraform with `elsudano/vmworkstation` provider v2.0.1 against the local VMware REST API at `http://127.0.0.1:8697/api` (`https=false`; `debug="NONE"` required). `terraform init` and `terraform validate` succeeded, and the VMware REST API could list the Ubuntu VM. However, the provider data source lookup `vmworkstation_virtual_machine` returned **HTTP 404**, so **no successful Terraform plan/apply or CPU modification was confirmed**. ## 7. Suggested repeat-build checks

```bash
# From linux-lab/ubuntu-2204
packer version
packer plugins installed
vmware -v
sha256sum "$HOME/Downloads/ubuntu-22.04.2-live-server-amd64.iso"
bash scripts/build.sh "$HOME/Downloads/ubuntu-22.04.2-live-server-amd64.iso"
```

Verify Ubuntu edition, SSH, network and the generated VMX after building. Do not overwrite the known-good output until the reconstructed files have passed a new test.
